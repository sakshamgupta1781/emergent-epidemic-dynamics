     Plan: LLM-powered analysis of experiment results (optional Anthropic key)

     Context

     Epidemic Lab is a standalone, dependency-free, browser-based SIR simulator
     that opens from
     file:// (no build, no server; scripts share window.App). Today it runs
     three experiment
     modes — Single, Compare (Control vs Test), and Batch (headless paired runs
     with a
     paired t-test across all three population modes) — and shows numbers and
     charts, but the user
     has to interpret them alone.

     This change adds an optional, LLM-powered "Analyze results" feature: the
     user pastes their
     own Anthropic Claude API key and clicks Analyze; the app sends the
     experiment's parameters
     (with plain-language meanings), the outcomes, and the full underlying data
     to Claude and
     shows a succinct, plain-English explanation of what happened and what to
     change. It works
     across all experiment modes and all population modes. The key is optional —
     every
     existing feature works without it, and the app stays fully offline until
     the user opts in.

     Because the app is a static file:// page with no backend, the only way to
     reach Claude is a
     direct browser fetch to https://api.anthropic.com/v1/messages using the
     user's key and
     the anthropic-dangerous-direct-browser-access: true header (Anthropic's
     supported
     browser-CORS path). The key never leaves the browser except in that request
     to Anthropic.

     Confirmed product decisions (from the user)

     - Key storage: localStorage on this device, with a Clear key button.
     Password-type
     input; a short "stored locally in your browser" hint. Never logged.
     - Model: default Opus 4.8 (claude-opus-4-8), with a picker: Opus 4.8,
     Sonnet
     (claude-sonnet-5), Haiku (claude-haiku-4-5).
     - Trigger: an Analyze button that reads the current on-screen state.
     - Send ALL the data (explicit): single/compare send the complete S/I/R time
     series (not
     just summary stats); batch sends every run's raw data points for all
     iterations and all
     three modes, plus the computed stats — so Claude has full context for its
     recommendations.

     Design

     New module: src/llm.js (App.LLM)

     Single place for key handling, the API call, and prompt building.

     - Key management: getKey(), setKey(key), clearKey(), hasKey(). Persists to
     localStorage['epidemicLab.anthropicKey'] (plus in-memory cache).
     getModel()/setModel()
     persist the chosen model to localStorage['epidemicLab.model'] (default
     claude-opus-4-8).
     - API call: analyze({ system, user }) →
     fetch('https://api.anthropic.com/v1/messages', …)
     with headers x-api-key, anthropic-version: 2023-06-01,
     anthropic-dangerous-direct-browser-access: true, content-type: 
     application/json; body
     { model, max_tokens: 1500, system, messages:[{role:'user',content:user}] }
     (non-streaming;
     responses are short). Returns the concatenated text blocks from content.
     Maps failures to
     friendly messages: 401 → "key looks invalid", 429 → "rate limited, try
     again", network/CORS →
     "couldn't reach Anthropic — check your connection".
     - Data → prompt helpers (pure functions, easy to unit-test):
       - describeParams(paramsObj, opts) — walks App.PARAMS, and for each param
     in scope for
     the current mode emits label, current value (formatted via App.UI.fmt), and
     its
     plain-language meaning from def.help.desc. Includes the global params
     (population, initially-infected, population mode).
       - seriesFromSim(sim) — extracts the full sim.history time series
     (t,s,i,r), the
     initial S/I/R, sim.peakInfected and its time, and final S/I/R
     (sim.counts()). If the
     history is very long (> ~300 points) it is evenly downsampled to ~300 and
     labeled as such;
     otherwise sent in full.
       - buildSingle(arm), buildCompare(control, test), buildBatch(batchData) —
     assemble the
     system + user prompts. System prompt fixes the persona and the "succinct,
     simple terms, no
     jargon" style and the mode-specific asks:
           - Single: explain why the infection peak occurred and the outcome for
     the overall /
     removed / susceptible populations, in plain terms.
         - Compare: state which parameters differ between arms; judge whether
     outcomes matched
     expectations (e.g. quarantine on in Test but off in Control → low peak /
     high remaining
     susceptible = working); flag surprises or no-change; and suggest what to
     change —
     including population and initially-infected — to get a representative
     reading.
         - Batch: for each population mode, say what happened; acknowledge
     expected results; and
     where a result is not expected or not statistically significant (p ≥ 0.05),
     suggest
     what to change (e.g. more iterations, larger population, different initial
     infected, a
     stronger intervention delta) to get a statistically significant reading.

     Batch runner surfaces raw per-run data — src/batch.js

     summarize() currently collapses the per-iteration arrays
     (cPeak/tPeak/cRem/tRem/dPeak/dRem)
     into means + stats and discards the raw points. To honor "send all runs":
     - runBatch(...)'s onDone will pass both the summary and the raw
     accumulator, e.g.
     onDone(summarize(acc), acc). acc already holds every iteration's
     control/test peak and
     removed values per mode — no new computation, just stop throwing it away.
     Rendering
     (renderResults) is unchanged (still consumes the summary).

     App wiring — src/app.js

     - Store the latest batch data on app state in wireBatchControls' done
     handler:
     state.lastBatch = { summary, raw, control:{…params}, test:{…params}, 
     shared:{population, initiallyInfected} }. Cleared on resetAll.
     - Add an Analyze handler that dispatches on viewMode:
       - single → App.LLM.buildSingle(arms.test) (single view shows the
     Test/Treatment arm).
       - compare → App.LLM.buildCompare(arms.control, arms.test).
       - batch → if state.lastBatch is set, App.LLM.buildBatch(state.lastBatch);
     otherwise show
     "Run the experiment first."
       - Each arm bundle already carries its sim (with history, peakInfected,
     counts()) and
     its live params; global params come from existing app state.
     - If !App.LLM.hasKey() → open the key panel and show an inline "Add your
     Anthropic key to use
     analysis" note instead of calling the API.
     - Wire the key input, model <select>, and Clear button to App.LLM.

     UI — index.html + styles.css

     - Analyze button (#analyzeBtn, e.g. "✨ Analyze") in Row 2 (Experiment)
     alongside the run
     controls — enabled in every mode.
     - Key/model settings as a compact <details> ("AI analysis") in the top bar:
     password
     input #apiKey, model <select> #analyzeModel (Opus 4.8 / Sonnet / Haiku),
     Clear key
     button, and the "stored locally in your browser" hint.
     - Results overlay #analysisModal (mode-agnostic; works over arms and the
     batch section):
     title, scrollable body, a loading spinner, an error area, and a Close
     button. A tiny safe
     text renderer (HTML-escape, then **bold**, -  bullets, and newlines → <br>)
     formats
     Claude's lightly-marked-up reply. Styled to match the existing dark theme.
     - Load src/llm.js after src/batch.js and before src/app.js in index.html.

     Critical files

     - src/llm.js (new) — key/model persistence, direct browser API call, prompt
     builders + data
     extraction. App.LLM.
     - src/batch.js — pass the raw per-iteration accumulator to onDone alongside
     the summary.
     - src/app.js — retain state.lastBatch, wire Analyze/key/model, dispatch per
     mode.
     - index.html — Analyze button, AI-analysis settings <details>,
     #analysisModal, script tag.
     - styles.css — settings cluster, Analyze button, modal/overlay + spinner
     styling.

     Reuse of existing code

     - App.PARAMS / def.help.desc (src/params.js) for parameter meanings.
     - App.UI.fmt(def, v) (src/ui.js) to format values exactly as the panels do.
     - sim.history, sim.peakInfected, sim.counts() (src/simulation.js) for time
     series.
     - App.Batch accumulator arrays (src/batch.js) for raw batch data; App.Stats
     for p-values.

     Verification

     - Syntax: parse-only check of all src/*.js via osascript -l JavaScript (no
     Node here).
     - Prompt-builder unit tests (JavaScriptCore, mock App objects):
     describeParams includes
     only in-scope params with their meanings; seriesFromSim downsamples a
     >300-point history to
     ~300 and preserves peak/initial/final; buildCompare names the differing
     params; buildBatch
     includes every raw run value and each mode's p-value/significance.
     - Key handling: setKey/getKey/clearKey round-trip against a stubbed
     localStorage;
     analyze() builds the correct headers/body (assert on a stubbed fetch) and
     never includes
     the key in any thrown/log message.
     - Manual/browser (user): open index.html; without a key, Analyze prompts to
     add one and
     all existing features still work offline. Add a key, pick a model; in
     Single/Compare run a sim
     then Analyze → succinct explanation appears in the modal; in Batch, run
     then Analyze → per-mode
     narrative with significance-based suggestions. Try an invalid key →
     friendly error. Clear key →
     Analyze prompts again. (No browser/Node in this environment, so this pass
     is the user's.)

     Security / privacy

     - Key is the user's secret: password input, localStorage only, Clear
     button, never logged or
     put in error text. Sent only to api.anthropic.com over HTTPS via the
     documented
     browser-direct header. Feature is fully optional; the app remains
     offline-capable without it.

     Out of scope

     - Streaming responses (short outputs; non-streaming keeps it simple).
     - Server-side proxying / hiding the key (impossible for a static file://
     app; user supplies
     their own key knowingly).
     - Extended-thinking mode (kept off for latency; can be added later for
     deeper batch analysis).
